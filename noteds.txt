Perbedaan dengan dan tanpa --headed:
	Tanpa --headed	Dengan --headed
Mode	Headless (tanpa tampilan)	Headed (dengan tampilan browser)
Browser	Tidak terlihat	Terlihat dan bisa dipantau
Kecepatan	Lebih cepat	Lebih lambat
Kegunaan	Untuk CI/CD atau production	Untuk debug dan melihat proses test
Resource	Lebih ringan	Lebih berat

Kapan pakai --headed?
Saat test gagal dan ingin lihat apa yang terjadi di browser
Saat debug masalah seperti timeout atau elemen tidak ditemukan
Saat ingin memastikan flow test sudah benar

Kapan tanpa --headed?
Saat sudah yakin test benar dan hanya ingin cek hasilnya
Saat jalankan banyak test sekaligus agar lebih cepat 👍

Manajemen Browser & Storage Playwright
1. Pengaruh Uninstall Browser Firefox dan WebKit
# Menghapus browser Firefox dan WebKit dari Playwright hanya berpengaruh di lokal saja dan tidak mempengaruhi:
package.json
playwright.config.js
Kode test
Repository/Git

# Yang terpengaruh hanya file binary browser yang tersimpan di komputer lokal. Jika suatu saat dibutuhkan kembali, cukup install ulang dengan perintah:
npx playwright install firefox
npx playwright install webkit

2. Mengapa Browser Tersimpan di AppData
# Playwright memisahkan antara package library dan browser engine:
Package library → tersimpan di dalam project di folder node_modules/@playwright/
Browser engine → tersimpan secara global di C:\Users\Muni\AppData\Local\ms-playwright\

# Alasan browser disimpan di AppData dan bukan di dalam project:
Browser engine berukuran sangat besar (500MB-1GB), sehingga jika disimpan di dalam project akan membuat project sangat berat
Semua project Playwright di komputer yang sama bisa berbagi browser yang sama tanpa perlu download ulang
Repository Git tetap ringan karena tidak menyimpan binary browser

3. Apakah Data di AppData Menghilang Setelah Testing
Data browser engine di AppData bersifat permanen dan tidak menghilang setelah testing selesai. Browser engine akan tetap ada sampai:
Diuninstall manual dengan npx playwright uninstall
Dihapus manual dari folder AppData
Dilakukan reinstall sistem operasi

4. Cara Menghemat Storage Disk C
# Beberapa cara untuk menghemat storage disk C:
1. Hapus hasil test setelah selesai:
rm -rf test-results
rm -rf playwright-report

2. Uninstall browser yang tidak dipakai:
npx playwright uninstall firefox
npx playwright uninstall webkit

3. Tambahkan ke .gitignore:
test-results/
playwright-report/
e2e/fixtures/

Pest memang lebih modern dari PHPUnit — syntaxnya lebih ringkas dan mudah dibaca.

Hubungan Pest dan PHPUnit:
Pest bukan pengganti PHPUnit, melainkan wrapper di atasnya. Di balik layar Pest tetap menjalankan PHPUnit, hanya tampilannya lebih elegan. Jadi keduanya bisa hidup berdampingan di project yang sama.

gunakan Pest untuk Unit + Feature test, dan Playwright tetap untuk E2E. Ketiganya saling melengkapi dan tidak bertabrakan.


Layer	Tool	Menguji apa
Unit	Pest	Fungsi/logika kecil (kalkulasi HPP, validasi)
Feature	Pest	Route, controller, database, auth
E2E	Playwright	Alur pengguna di browser (klik, form, UI)







Lebih lengkapnya feature test di Laravel/Pest menguji satu fitur secara menyeluruh dari sisi HTTP — artinya mensimulasikan request seperti yang dilakukan browser nyata, tapi tanpa browser.

Yang diuji dalam satu feature test bisa mencakup sekaligus:

1. Route — apakah URL bisa diakses
get('/client/dashboard')->assertOk();
2. Auth/Middleware — apakah hanya user yang login bisa akses :
get('/client/dashboard')->assertRedirect('/login'); // tanpa login
3. Controller — apakah logika controller berjalan benar :
post('/client/pallet-request', $data)->assertRedirect();
4. Database — apakah data benar-benar tersimpan/berubah
assertDatabaseHas('pallet_requests', ['jenis_palet' => 'Palet Kayu Jati']);
5. Response/View — apakah halaman menampilkan konten yang benar
get('/client/referensi')->assertSee('Referensi Produk');

Tidak butuh server berjalan

Cepat

pest tak perlu memakai php artisan serve dan npm run dev namun tetap nyalakan laragon karena Pest butuh koneksi ke database sipalet_testing.
Pest bekerja sepenuhnya di sisi PHP tanpa browser dan tanpa server HTTP.
jadi cukup jalankan ./vendor/bin/pest atau php artisan test
dan tidak masuk ke database.
cara kerja nya:
php artisan test dijalankan
        ↓
Laravel buat database SQLite di RAM (:memory:)
        ↓
Migrasi dijalankan otomatis di database RAM
        ↓
Test berjalan, data dibuat di RAM
        ↓
Test selesai, database RAM langsung hilang
        ↓
Database MySQL utama kamu tidak tersentuh sama sekali

dan pest tidak memakan memori laptop karena pemakaian setelah memori dipakai akan dilepaskan lagi
RAM    → sekitar 30-80 MB (sangat ringan)
CPU    → spike sebentar saat test jalan, lalu kembali normal
Waktu  → biasanya selesai dalam 2-10 detik
Disk   → 0 (tidak nulis ke disk sama sekali)

Middleware adalah penjaga/filter yang berjalan sebelum request masuk ke controller.
Analoginya seperti satpam gedung:
User request → Middleware (cek dulu) → Controller (proses) → Response

Jadi yang kita test di RouteMiddlewareTest.php adalah memastikan kedua middleware ini bekerja benar
Guest → coba akses /client/dashboard → middleware 'auth' blokir → redirect /login ✅
Klien → coba akses /admin/dashboard → middleware 'isAdmin' blokir → 403 ✅
Admin → akses /admin/dashboard → lolos semua middleware → 200 ✅

Http::fake() dari Laravel yang mencegat request HTTP sebelum keluar ke internet dan menggantinya dengan response palsu yang kita definisikan sendiri.
Cara kerjanya:
ZoomService::getAccessToken()
        ↓
Http::fake() mencegat sebelum keluar
        ↓
Mengembalikan response palsu { "access_token": "fake-token" }
        ↓
API Zoom sungguhan tidak pernah dipanggil

Analoginya seperti double/stunt di film — yang beraksi bukan aktornya langsung, tapi penggantinya yang dibuat seolah-olah sama.
Kenapa tidak hit API langsung?
❌ Butuh koneksi internet
❌ Butuh kredensial Zoom valid
❌ Bisa kena rate limit Zoom
❌ Test bisa gagal bukan karena kode, tapi karena jaringan
❌ Lambat
Dengan Http::fake():
✅ Tidak butuh internet
✅ Tidak butuh kredensial asli
✅ Selalu konsisten
✅ Cepat
✅ Fokus menguji logika kode kamu, bukan infrastruktur Zoom


unit test tidak pakai database jadi ModelRelationTest tidak butuh RefreshDatabase. Pastikan tests/Pest.php hanya apply RefreshDatabase ke folder Feature saja
Unit test tidak pakai database — itulah intinya.
Unit test menguji logika murni sebuah fungsi/method secara terisolasi, tanpa:
❌ Database
❌ HTTP request
❌ File system
❌ External
Contoh nyata di SIPALET:
ModelRelationTest — menguji apakah relasi model terdefinisi dengan benar tanpa perlu data di database
ZoomServiceTest — menguji apakah logika ZoomService mengirim request dengan benar tanpa hit API sungguhan
Manfaat unit test:
Sangat cepat karena tidak ada I/O
Mudah debug karena scope kecil
Menemukan bug di level terkecil sebelum menyebar
